# Saved Intelligence Alerts Design

## Product Shape

PredictArena's next product step is a saved intelligence loop: users can keep a small personal research workspace around the markets and filters they repeatedly inspect. The primary user remains a prediction-market researcher, operator, or agent builder. The feature should help them answer: "What changed since I last looked, and what should I research first today?"

The first version must remain accountless and in-app. The client creates a high-entropy `workspaceId`, stores it locally, and sends it to the saved-intelligence APIs. This id is not authentication and must not protect sensitive data. The server stores only bounded preferences, watchlist entries, alert state, and lightweight evaluation snapshots. A user who clears local storage may lose access to that local workspace. That is acceptable for this version and must be documented.

The recurring workflow is:

1. Open `/intelligence`.
2. Save the current market radar filter as a named research preset.
3. Watch one or more supported markets from the radar or research panel.
4. Return later and refresh saved intelligence or open the daily queue.
5. Confirm the last evaluated timestamp, stale state, or evaluation failure state.
6. Review alert reasons, changed metrics, data-health warnings, and near-expiry items.
7. Select an item to inspect the existing read-only research, agent comparison, and paper-follow panels.

This workflow must not become a trading system. Alerts are prompts to inspect research context, not buy/sell/follow recommendations.

## Core Concepts

### Local Workspace Identity

`workspaceId` is generated by the client using random UUID or stronger entropy and stored in browser local storage. Server APIs validate shape and length, but must treat it as a routing key for non-sensitive preference data rather than as proof of identity.

The server must cap stored state per workspace:

- saved filters: maximum 20
- watched markets: maximum 100
- retained alerts: maximum 200
- saved filter name: maximum 80 characters
- watch note or label: maximum 160 characters

Responses must never include private keys, service-role keys, cron/proof/admin secrets, raw provider/RPC errors, stack-like diagnostics, internal URLs, request headers, server config, raw market payloads, lock owners, or idempotency keys.

Every workspace-specific mutation must include `workspaceId` in the JSON body. Workspace-specific GET endpoints use `workspaceId` as a query parameter. PATCH and DELETE endpoints must load the target resource and verify it belongs to the supplied workspace before mutating. If the resource exists for another workspace, the API must return `not_found` with HTTP `404` rather than revealing cross-workspace existence. Missing or invalid workspace ids return `invalid_request` with HTTP `400` and zero side effects.

### Saved Filter

A `SavedIntelligenceFilter` is a named snapshot of safe market-radar query fields:

- `asset`
- `conditionType`
- `confidence`
- `source`
- `sort`
- `minEdgeBps`
- `maxExpiryDays`
- `minLiquidity`
- optional `minOpportunityScoreBps`
- optional `minDataHealthScoreBps`

Saved filters may be evaluated against the existing market intelligence read model. Evaluation records a bounded snapshot: matched count, top market ids, top opportunity score, top edge, top data-health score, evaluated timestamp, freshness status, and optional sanitized failure reason. The snapshot is used only to explain changes and does not store raw provider payloads.

Threshold schema:

- `minOpportunityScoreBps`: integer `0..10000`, default `0`
- `minDataHealthScoreBps`: integer `0..10000`, default `0`
- `edgeChangeThresholdBps`: integer `100..5000`, default `500`
- `disagreementChangeThresholdBps`: integer `100..5000`, default `500`
- `dataHealthDropThresholdBps`: integer `100..5000`, default `1500`
- `nearExpiryHours`: integer `1..168`, default `24`

PATCH may update threshold fields, saved filter name, safe filter query fields, and enabled state only.

### Watched Market

A `WatchedMarket` pins a known public market id or clob/gamma identity returned by the intelligence catalog. It stores safe public metadata and user-controlled label/note fields, not raw payload. If the watched market disappears, expires, or becomes unsupported, the watch item remains visible with a degraded reason rather than silently disappearing.

### Alert

An `IntelligenceAlert` is deterministic and in-app only. It references a saved filter or watched market and carries:

- alert id
- reason code
- severity: `info`, `watch`, or `urgent`
- current safe market or signal ids when available
- previous and current metric snapshot
- deterministic summary
- created timestamp
- read/dismissed state

Required first-version reason codes:

- `new_high_priority_market`: a saved filter now matches a market above the configured opportunity/data-health thresholds that was not in the previous top snapshot.
- `edge_changed`: a watched market or saved-filter top market changed absolute best-agent edge by at least the configured threshold, default `500` bps.
- `agent_disagreement_changed`: the probability gap between market implied probability and best agent probability changed by at least the configured threshold, default `500` bps.
- `data_health_degraded`: data health fell below the configured threshold or dropped by at least `1500` bps.
- `near_expiry`: a watched or queued market is within the configured expiry window, default `24` hours.

Alerts must not be generated from invented news context or external LLM summaries.

### Refresh and Freshness

Saved-intelligence evaluation is manually triggered in v1 through `POST /api/intelligence/alerts/evaluate` and a visible "refresh saved intelligence" control in `/intelligence`. The UI may also call evaluation after creating a saved filter or watch item, but it must still expose the last evaluated state.

Evaluation returns:

- `evaluatedAt`
- `freshness`: `never_evaluated`, `fresh`, `stale`, or `failed`
- `createdAlertCount`
- `suppressedDuplicateCount`
- `updatedSnapshotCount`
- optional sanitized `failureReason`

Freshness is `stale` when the latest successful evaluation is older than 24 hours or when the underlying market intelligence freshness indicates degraded data. If evaluation fails, the API must preserve the last successful snapshots when available and return a sanitized `evaluation_failed` state rather than hiding saved filters, watchlist, or existing alerts.

### Daily Research Queue

The daily queue is a read model, not a task manager. It merges:

- watched markets
- top matches from saved filters
- unread alerts
- current opportunity/risk/data-health scores
- expiry urgency
- accountability state

The queue returns a bounded list sorted by urgent alerts, near expiry, high opportunity, strong disagreement, and data-health degradation. Each queue item links back to existing `/intelligence` research state. It must explain why the item appears using safe reason codes and deterministic summaries.

## API Shape

All endpoints use zod or equivalent structured validation. Invalid requests return `invalid_request` with issues. Unknown resources return `not_found`. Public server errors return sanitized reason codes.

Common error semantics:

- malformed request or invalid workspace id: HTTP `400`, `{ "reason": "invalid_request", "issues": [...] }`
- item limit exceeded: HTTP `409`, `{ "reason": "saved_intelligence_limit_reached", "limit": number }`
- duplicate watch item: HTTP `200`, returning the existing watch item with `{ "duplicate": true }`
- duplicate active alert during evaluation: HTTP `200` evaluation result with incremented `suppressedDuplicateCount`
- target resource absent or belongs to a different workspace: HTTP `404`, `{ "reason": "not_found" }`
- persistence unavailable: HTTP `503`, `{ "reason": "saved_intelligence_unavailable" }`
- sanitized unexpected failure: HTTP `500`, `{ "reason": "saved_intelligence_error" }`

- `GET /api/intelligence/workspace?workspaceId=...`
  - returns workspace summary, saved filters, watched markets, unread alert count, and daily queue preview
- `GET /api/intelligence/saved-filters?workspaceId=...`
  - lists saved filters and latest evaluation snapshots
- `POST /api/intelligence/saved-filters`
  - body includes `workspaceId`; creates a saved filter from validated query fields, thresholds, and a bounded name
- `PATCH /api/intelligence/saved-filters/[filterId]`
  - body includes `workspaceId`; updates name, filter query, thresholds, or enabled state after workspace ownership check
- `DELETE /api/intelligence/saved-filters/[filterId]`
  - body includes `workspaceId`; deletes a saved filter after workspace ownership check and keeps historical alerts marked as orphaned safe records
- `GET /api/intelligence/watchlist?workspaceId=...`
  - lists watched markets with current intelligence state when available
- `POST /api/intelligence/watchlist`
  - body includes `workspaceId`; adds a known public intelligence market id to the watchlist
- `DELETE /api/intelligence/watchlist/[watchId]`
  - body includes `workspaceId`; removes a watch item after workspace ownership check without deleting market or signal data
- `GET /api/intelligence/alerts?workspaceId=...`
  - lists alerts with filters for `unread`, `reason`, and `severity`
- `POST /api/intelligence/alerts/evaluate`
  - body includes `workspaceId`; evaluates saved filters and watchlist entries for the workspace, updates freshness snapshots, and creates bounded in-app alerts; it must not run agents, mutate markets, or send transactions
- `PATCH /api/intelligence/alerts/[alertId]`
  - body includes `workspaceId`; marks an alert read/unread or dismissed after workspace ownership check
- `GET /api/intelligence/daily-queue?workspaceId=...`
  - returns the prioritized daily research queue

Mutation endpoints only modify user preference and alert state. They must not call Arc commit, proof transaction, autonomous run, demo resolution, Polymarket trading, market scan save, or signal generation paths.

## Persistence

Use the existing persistence abstraction first, but saved-intelligence state must live in an independent namespace or subdocument such as `savedIntelligence` keyed by workspace id. Implementation must preserve existing arena, signal, run, ops, proof, autonomy, claim, lock, leaderboard, and resolution state exactly as-is while adding saved-intelligence methods. If Supabase schema support is not present, local fallback must still run without configuration.

Data writes must be bounded and idempotent where appropriate:

- saving the same market twice should return the existing watch item or a controlled duplicate reason
- alert evaluation should not create duplicate unread alerts for the same workspace, source, reason code, market, and current metric snapshot
- deleting saved preferences must not delete market, signal, run, resolution, proof, Arc, or leaderboard data
- replacing or migrating local persisted state must preserve all existing top-level arena/autonomy/proof fields and tolerate older local JSON files without a `savedIntelligence` key

## UI Shape

`/intelligence` should add a compact saved-intelligence rail or toolbar:

- save current filter
- saved filter selector
- watched markets shortcut
- alert center button with unread count
- refresh saved intelligence button with last evaluated, stale, or failed state
- daily queue section
- mark read/dismiss controls for alerts
- watch/unwatch controls for market rows and selected research

The UI must keep the current dense research workflow intact. Saved controls should help users return to research, not replace market radar, research detail, agent comparison, or paper-follow.

Desktop acceptance:

- first viewport still exposes market radar and research context
- saved filter/alert/queue affordances are visible without dominating the screen
- queue items show reason, severity, current score snapshot, and link to research
- the saved-intelligence area shows whether it was saved on this device/local workspace and shows last evaluated or stale state

Mobile acceptance:

- saved filters, alert center, queue, market radar, research, agent comparison, and paper-follow remain reachable without horizontal scrolling
- alert action buttons do not overlap text or hide core research state
- local workspace disclosure remains visible in saved-state empty or settings surfaces without taking over the research flow

Copy must use "research queue", "watch", "review", "changed", and "data health" language. It must not say "buy", "sell", "trade now", "copy", "guaranteed", or "recommended position".

## Review and Risk

This change adds bounded user preference mutations and in-app alert state. It requires:

- product/usefulness review: does it create a real daily return loop without confusing alerts for financial advice?
- engineering/security review: are workspace ids treated as non-auth identity, writes bounded, responses sanitized, and mutation paths isolated from transaction/agent-run behavior?
- no-financial-advice review: alerts must point to research context, not recommendations.

Implementation should proceed contract-first: freeze types and validation schemas, add persistence and API tests, then wire UI and e2e coverage.
